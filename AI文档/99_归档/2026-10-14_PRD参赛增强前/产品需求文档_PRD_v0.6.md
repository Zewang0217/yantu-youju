# 推免个性化推荐系统 · 产品需求文档（PRD）

需求提出：用户；文字整理：Codex（AI助手）。创建日期：2026-10-13；更新日期：2026-10-14（北京时间）。

本稿将已讨论的产品需求整理为连贯说明，用于统一产品目标、MVP范围和核心业务规则。展示数量、排序算法、字段结构和实现参数等在后续设计中确定。用户原文与One-Pager保留；本稿尚未整体确认，不作为已定稿声明。

## 1. 产品目标与用户

面向所有有推免择校需求的学生，提供基于个人情况的院校与专业推荐，帮助用户减少分散查找、手工整理和判断政策的负担，获得有理由、有来源的择校建议。

产品由两部分组成：

1. 自动获取、整理和积累推免相关资料，保留可复用的院校来源入口。
2. 通过对话构建用户画像，从资料中寻找适合的申请机会，主动复核后提供个性化推荐。

学生是推荐服务的使用者。管理员负责发起全局资料更新、查看更新情况与访问异常告警。管理员操作不改变信息自动获取的产品主线。

## 2. MVP范围与长期方向

| 维度 | MVP范围 |
|---|---|
| 院校 | 聚焦985／211及部分值得关注的新型高校，具体名单由后续调研整理 |
| 专业 | 目标专业为计算机相关方向，包括软件工程；不限定用户本科专业 |
| 申请场景 | 夏令营、预推免、补录、二次推免及其他新增批次／机会，覆盖相关新政策 |
| 主要信息 | 申请政策、条件、时间、材料、报名方式，以及官方可查证的历史参考 |
| 推荐对象 | 院校、院系、专业及对应申请机会；按各院系／专业的具体制度判断 |
| 产品交付 | 多个个性化推荐、推荐理由、相关政策和来源，以及需要用户核实的具体事项 |
| 使用方式 | 纯对话，可通过可交互卡片回答问题；用户画像可复用 |
| 时点范围 | 正常推荐当前能申请的机会；报名状态确实查不到的符合条件院校作明确末尾提示 |

长期逐步扩展到所有专业或尽可能多的专业，按用户选择的目标方向提供推荐。不同院校、院系、专业、年度、招生阶段和批次的制度存在差异，产品应能够接纳新增机会与政策类型，具体可扩展模型在后续领域分析中设计。

后续版本方向：

- 导师／课题组推荐；
- 个人申请计划、排期等申请过程辅助；
- 上传简历、成绩单等附件并提取画像信息。

这些能力属于后续版本，MVP聚焦推免政策与辅助择校。

## 3. 核心产品能力

### 3.1 自动信息获取与资料积累

按院校发现并获取相关公开资料，整理基本推免情况及院系／专业的政策和申请规则；信息应附来源URL，经过复核后留存，供推荐复用。

首次探索同时积累招生网站、院系入口等线索。后续获取优先复用已知入口，必要时补充探索；新年度可一键启动资料获取与整理流程。

历史参考是MVP能力，至少包含官方可查证的：

- 往年通知、政策、申请条件、时间和考核方式；
- 往年入营、接收或录取情况，以及可获取的背景统计。

历史资料按年度区分，与当前政策共同为推荐提供参考；具体回溯年限由后续资料调研和采集设计确定。

### 3.2 资料更新与复核

资料更新支持两种已确认触发：

- 根据已有资料找到推荐候选院校后，主动检查相应来源是否出现新政策、规则或申请机会；
- 管理员主动开启全局已收录院校的信息检查与更新。

发现变化后更新资料，并重新判断相关候选。探索能力应可扩展、可插拔，以适应不同来源和政策类型；具体实现留到技术设计。

复核作为推荐流程中的一个步骤，允许耗时。无法访问时标记并跳过；多次无法访问时向管理面板发出warn告警。具体重试、告警和缓存参数在后续设计中确定。

### 3.3 对话画像与复用

通过多轮对话了解个人情况，UI可使用可交互卡片承载回答。基础画像范围包括：

- 本科院校、本科专业、预计毕业年份；
- 目标方向；
- GPA／成绩排名／百分比；
- 英语、科研和竞赛情况；
- 可选的个人偏好。

每个用户的画像后续可复用。每次新对话开始时，先询问用户是否需要修改已有画像，再沿用或更新；无已有画像时，通过对话建立。

个人信息缺失或口径不清时进行澄清，无法判断的具体点要明确标注。具体字段口径参考已完成的[画像字段调研](D:/Zewang/newProject/ICT/AI文档/02_前期调研/计算机推免用户画像字段调研.md)，在后续需求规格与设计中细化，不将所有建议字段自动设为必填。

### 3.4 科研突出判定与申请条件筛选

在院校检索／调研前增加科研突出判定，将该标记作为后续筛选条件之一；具体判定标准后续研究。

按各院系政策使用科研突出标记：明确允许放宽的，检查对应条件；没有放宽条款的，仍严格筛选。系统的科研判断不等于院校已批准放宽。

依据各院系／专业的实际要求筛选，明确不符合者淘汰；暂时无法判断者保留在候选，标注无法判断的具体点，让用户自行核实或补充信息，由系统重新判断。

### 3.5 个性化推荐与解释

综合个人背景、专业适配、官方历史参考和用户偏好，对候选统一排序。具体算法和权重后续研究。

提供多个院校／院系／专业推荐，说明为什么适合该用户，并展示对应政策和来源。结果可采用“学校—院系—专业”层级；存在第二批等额外批次时再标注。业务上保留具体申请机会的区别，避免混用不同项目的政策。

展示数量、加载方式和页面布局在后续交互与实现设计中确定。

## 4. 主要使用流程

**资料准备：**管理员发起信息获取 → 自动发现与整理资料 → 来源复核 → 留存资料和可复用入口 → 后续按年度或手动全局更新。

**学生咨询：**

1. 新对话开始，确认已有画像是否需要修改；无画像时建立画像。
2. 通过多轮对话澄清个人情况与可选偏好，进行科研突出判定。
3. 从已有资料中检索符合目标方向的院校／院系／专业与申请机会，按对应条件筛选。
4. 主动复核候选院校来源，检查新规则与机会，更新资料并重新判断；访问失败项标记跳过。
5. 对候选统一排序，输出多个推荐、理由、政策和来源，明确说明个人条件中的未知点。
6. 对符合个人条件但报名开放状态确实无法查证的院校，在列表末尾提示，并给出核实或行动建议。

## 5. 核心业务规则

| 情况 | 产品处理 |
|---|---|
| 明确当前不能申请 | 不进入推荐候选；不将已截止或未来机会当作当前可申请机会 |
| 个人条件明确不符合适用要求 | 淘汰；偏好不抵消申请门槛 |
| 个人条件暂时无法判断 | 保留候选并统一排序，明确标注未知点，支持补充后重新判断 |
| 科研突出且政策允许放宽 | 检查该院系的对应放宽条件；无放宽条款则仍严格筛选 |
| 官方资料能够查阅，但确实查不到是否开始报名；个人条件符合 | 在列表末尾提示报名状态未知，提供建议行动，不声明已确认开放 |
| 复核无法访问来源 | 标记并跳过；多次失败向管理员告警 |
| 没有找到历史资料 | 仍可推荐，备注缺失并简述可查证的原因；无依据时不猜测为新专业 |
| 历史政策与当前机会 | 历史信息提供参考，不能直接冒充当前有效规则 |
| 全局已有院校信息更新 | 仅管理员可触发 |
