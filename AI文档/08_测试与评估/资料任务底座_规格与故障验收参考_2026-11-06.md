# 资料任务底座：最小验收与恢复边界参考

用于本轮SQLite单机任务底座及离线bundle校验→适用性分析工作流的实现/复核。依据[SRS OPS-02~05及§5.1](../05_需求分析/软件需求规格说明书_SRS.md)、[数据与工具契约§3.1/4/5](../07_详细设计/数据与工具契约设计.md)与[开发盘点工作单2](../09_开发与交付/开发现状与后续任务_2026-11-05.md)。本参考没有执行新增实现测试，也未联网、读取密钥、调用模型或发布政策。

## 完成声明应分三层

1. **可验收：单机任务账本与产物恢复。** run/task/step/attempt/call、预算、终态、取消、租约和审计持久化；任务产物与步骤完成同事务；旧worker不提交任务产物；真实离线工作流可执行、查询、恢复。
2. **本轮可证明：默认工作流无发布副作用。** bundle检查与inspect_applicability均不调用PublicationRepository，不联网、不读模型配置；报告仍not_published/hold。需要明确测试这个不变量。
3. **本轮不能自动宣称：已实现发布库fencing或完整OPS-03。** 07 publish_verified要求发布写入时同事务校验task仍有提交权和当前epoch。SQLite任务表与既有文件发布库不是同一事务，前置检查lease再调用文件write仍存在取消/抢占竞态。未接线前应在开发盘点保留该项，不能把“只读任务没有发布”称作“生产发布中断恢复已验证”。

任务控制状态、源报告数据状态、正式发布状态必须分别保存。源partial/字段unknown属于业务结果，不能笼统改成系统异常；最终目录unknown不应使一个已经完成范围分析的任务永久running。若应用选择将源缺损映射task partial，应写明聚合规则，且仍保留已完成步骤和报告。

## 核心不变量

- 幂等键只定位任务，不能代替输入版本。相同key且输入/计划/目标/预算配置摘要不同，明确冲突；不能静默返回原目标结果或改写原任务。
- checkpoint是已提交的步骤产物引用，不是“handler已经执行过”的内存标记。恢复跳过已提交步骤；对未提交的调用只能安全重放幂等操作。
- “产物恰好一次提交”和“外部调用恰好一次执行”不同。进程可在实际调用后、结果提交前退出，此时需要保守usage_pending和幂等重放，不得承诺任意工具exactly-once。
- 写入权限至少检查taskId、owner、lease epoch、未取消、有效租约及deadline；校验和产物/步骤/任务状态/关键审计写入必须在同一事务内。
- 预算预留在调用前原子完成；实际用量与预留不混同；未知仍持有保守额度，实际超估也如实入账并阻止后续新调用。
- 终态不因resume而复活。需要新预算/新输入的重跑应建立新run关联旧任务，保留原失败/取消/usage证据。
- 只对白名单错误且操作幂等时重试。403/认证/编程错误不自动重试；Retry-After不得被截短后提前重试。

## 最小验收矩阵

| 组 | 触发与观察 | 必须证明 |
|---|---|---|
| 提交/幂等 | 同key提交相同冻结输入两次 | 同task/run或明确幂等复用，不增加步骤或调用 |
| 提交/冲突 | 同key但target、输入digest、handler版本或预算改变 | 明确冲突，原任务与产物不变 |
| 输入固定 | 提交后bundle或源blob被替换/损坏 | 不读新内容冒充旧任务成功；错误可定位，原预期版本仍可查 |
| 正常路径 | 两个只读真实步骤顺序完成 | request/run/task/step/attempt/call有可关联记录，输出可读且hash可核对 |
| 检查点恢复 | 步骤1提交后中断、换store实例恢复 | 步骤1不再执行，只做步骤2；已提交产物不改写 |
| 实际进程退出 | 调用已dispatch、结果尚未commit时退出 | 恢复保留旧attempt；旧调用usage_pending，不把额度退0 |
| 未发出恢复 | reserve后、dispatch前退出 | 能证明未发送的预留释放；新attempt仍受次数/时间预算约束 |
| 并发领取 | 两个独立连接/worker领取有效任务 | 最多一个有效owner/epoch；第二个不执行handler |
| 过期接管 | worker A租约过期，B取得新epoch，A后返回 | A不能写产物或完成步骤；B状态不被A覆盖 |
| 空窗过期 | 无B接管，但A租约已经到期才写 | 同样不能提交；不能以“暂无新worker”绕过租约 |
| 取消/排队 | queued/retry_wait阶段取消后resume | 直接稳定cancelled，不新增调用 |
| 取消/执行 | 已dispatch时取消，handler随后返回 | 结果不成为新checkpoint；未知在途用量保留；已完成旧步骤仍可追溯 |
| 取消/竞态 | 结果提交与cancel并发 | 符合事务线性顺序；不能半完成半取消，也不追溯撤销已提交的终态 |
| deadline | 首次调用前耗尽、调用后才耗尽、等待重试时耗尽 | 停止新调用；不把超期结果标完成；partial/failed聚合可说明 |
| 已知重试 | RATE_LIMITED/TEMP_UNAVAILABLE，调用幂等且预算足够 | 持久retry_wait和notBefore；到期前不执行，无busy-loop/sleep |
| Retry-After | 服务要求等待大于本地退避 | 至少遵守该等待；超出deadline/策略上限则停止，不提前重试 |
| 不可重试 | FORBIDDEN/AUTH_REQUIRED、程序TypeError | 不重试；编程错误重抛并脱敏记录，不能转业务unknown |
| 重试上限 | 持续可重试错误 | attempt数量有界，历史失败不丢失，终态明确 |
| 并发预算 | 多个预留竞争同父账本最后额度 | 原子扣减/预留，只允许剩余额度内的调用 |
| 结算/退款 | 预计大、已知实际小；显式未发送 | 差额释放/未发送释放；spent与held可区分 |
| 用量未知 | 超时或worker退出且可能计费 | usage_pending计入held，不能以0释放；恢复不会突破总预算 |
| 对账幂等 | 同callId同实际usage结算两次，再以不同usage结算 | 同值无重复扣款，异值冲突；不能改写已确认账本 |
| 实际超估 | 实际用量大于estimate或剩余额度 | 如实记账/可见超额，后续新调用停止；不截断实际值装成守住预算 |
| 持久化失败 | 产物/步骤/任务/审计事务commit故障 | 无部分可见成功；异常上抛，不能无审计标完成 |
| 摘要/产物损坏 | 已完成checkpoint blob/hash不一致 | fail fast，不重放已完成步骤偷偷修复或返回空报告 |
| 查询/隐私 | 任意异常message/cause放合成敏感标记与URL query | CLI/log不回显；仍可查errorCode、关联ID和栈位置 |
| 默认隔离 | 真实离线流程执行及恢复 | 模型/网络调用0，不读密钥，不写PublicationRepository；结果not_published/hold |
| 状态区分 | 分析正常结束但源partial、目录unresolved | 清楚区分任务控制状态与数据/发布状态，不常驻running也不伪称政策已核验 |

矩阵应优先按可观察行为组合测试，不需为每个表字段写镜像断言。并发领取/预算用独立SQLite连接；时间与重试注入时钟，不用sleep；进程恢复至少保留一个真正跨进程或独立store实例的证据，不能全靠同对象内存状态。

## 日志、错误及版本关联

建议任务查询默认只返回生成的关联ID、状态/原因码、步骤计数、handler/输入/产物版本、spent/held/pending。完整源文本、原始异常message、凭据、URL query和任意用户payload不进入结构日志。

控制状态迁移、预留/dispatch/settle/reconcile、checkpoint提交与lease/cancel事件应可沿requestId→runId→taskId→stepId→attempt→callId追溯。DB审计与checkpoint同事务；外部日志导出并不替代本地关键审计。存储故障不能被通用except写成“partial且成功返回”。

版本至少包括：任务schema、handler kind/version、冻结输入bundle摘要、target、预算策略和输出artifact摘要。恢复时handler版本不存在/不兼容，应停止并指出需要重跑的步骤，不能以当前同名函数代替历史版本继续运行。

## 范围建议

可以将本次完成表述为：“单机持久任务、预算与检查点恢复底座完成，并接入只读离线适用性核验；任务产物提交具租约校验，未知usage与失败可查询。”

应保留为剩余项：既有事实发布库与任务租约的同事务fencing、真实网络/模型适配器的细粒度预算和供应商usage对账、多机租约与调度、完整管理鉴权/UI、生产进程隔离或强制终止长耗时工具。同步函数的deadline若只在调用边界检查，要明确这是软时间预算，不声称可硬中断任意解析器或阻止供应商继续计费。
