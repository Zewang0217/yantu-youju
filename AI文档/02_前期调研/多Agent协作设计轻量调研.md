# 多Agent协作设计轻量调研

作者：Codex（AI助手）。调研日期：2026-10-14（北京时间）。范围：官方协作模式资料与本项目下一阶段设计建议；未实测框架，不决定Agent数量、推荐算法或技术选型，不扩展PRD产品范围。

## 1. 官方资料确认的设计要点

**固定编排和自主Agent可以组合。**Anthropic区分预定义路径的workflow和模型动态决定步骤、工具使用的Agent，并介绍串行、并行、协调者与worker、评估反馈循环等模式。文章发表于2024-12-19，页面提示工具生态已有变化，这里只采用模式层面的依据。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

**先明确谁掌握控制权。**LangChain区分主Agent调用子Agent、交接控制权、路由和自定义workflow；强调让各Agent获得其任务所需的上下文。[Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)

**任务运行需要显式状态和可检查输出。**LangGraph示例以状态图组织节点、分支、并行和反馈循环，支持结构化输出、工具调用以及运行持久化和流式过程。[Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

**协作循环需要停止机制。**AutoGen提供消息数量、token使用、超时、外部停止等终止条件，条件可组合。它说明终止条件的表达方式，不能直接作为本项目性能保证。[Termination](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html)

## 2. 应用于两部分系统的初步建议

以下为基于现有PRD的设计推论，不是官方资料或用户已确认的架构。

信息系统单独设计Agent协作模块：任务分配、招生入口探索、资料获取与提取、来源复核、更新结果汇总。外层编排明确顺序和完成条件；官网入口失效、出现新政策等情况，可以交给有范围与停止条件的探索Agent决定补查步骤。不同院校可以并行处理，同一条资料的提取与复核则存在先后依赖。

推荐系统也单独设计Agent协作模块：对话画像、科研突出判定所需分析、候选条件分析、主动复核请求、推荐理由生成。明确硬性规则的筛选可由普通程序执行；含义解释或补充澄清可由Agent辅助。科研突出标记仅在院系政策允许时使用，标准尚待研究。

两者之间用“复核任务—复核结果”连接：推荐侧携带院校／院系／项目范围和现有资料版本发起检查；信息侧返回最新政策与来源、检查状态、检查时间和更新后的版本；推荐侧以返回资料重新筛选。访问失败按已确认需求标记并跳过，多次失败向管理面板告警；报名开放状态未知的符合条件项目依PRD作为末尾提示，不能冒充已确认开放机会。

业务模块与Agent不是一一对应：存储、明确规则校验、任务状态管理仍有独立职责。角色也不等于运行实例，例如一个“院校探索角色”可以产生多个按校处理的worker，不必给每所学校另写一套Agent。主Agent调用子Agent并返回结果与Agent接管对话应分清；是否需要控制权交接，由后续交互设计决定。

## 3. Agent设计文档应明确什么

建议两个系统各自写Agent协作设计，采用同一说明模板：职责与边界、输入输出、可用工具、所需上下文、控制权与调用对象、完成标准、失败与停止处理、过程记录和验证方法。输入输出采用明确的任务与结果结构，而非仅传自由文本；政策结论必须关联来源和对应原文，第二个Agent认可并不能替代证据核查。

区分三种信息：本次对话／任务状态、发送给特定Agent的上下文、可长期复用的画像及院校入口／政策资料。长期复用靠有版本的存储设计，不依赖Agent“记得”。明确谁读取和修改哪些资料，以及并行更新如何汇总、避免覆盖。

可观测记录建议包括任务标识、步骤与工具结果、使用的资料版本、失败原因、耗时及模型用量。评估同时关注采集与证据准确性、条件筛选一致性、更新成功率、推荐理由依据和用户任务效果；分别验证Agent步骤与完整链路，不能只看最终文字是否流畅。

## 4. UML与下一步设计的结合

| 工具／图 | 在本项目中表达什么 |
|---|---|
| 概念类图 | 院校—院系—专业—机会—政策—证据，以及画像之间的业务关系 |
| 组件图 | 两大系统、Agent协作模块、规则服务、工具与存储的职责和依赖 |
| 活动图／泳道 | 两条主流程、串并行、分支、复核反馈和人机澄清；区分Agent、普通程序和用户职责 |
| 时序图 | 一次采集或推荐中的调用、返回、控制权、上下文传递，以及跨系统复核消息 |
| 状态机图 | 等待输入、执行、复核、完成、失败、跳过等任务状态与转移条件 |

建议顺序：领域与信息模型 → 两条业务流程 → 系统职责及Agent角色划分 → 输入输出与跨系统契约 → 关键交互与异常状态 → 工具／存储／平台映射 → 验证与评审。各阶段可以迭代，角色划分会反过来校正架构。UML辅助解释设计；Agent说明表和数据契约补充图不能表达的细节。PlantUML可用来维护图源，工作流运行图留待实现工具确定后使用。

当前不增加穷尽式PRD问卷，也不提前固定Agent数量、框架、重试次数或排序权重；下一阶段先把两套Agent协作设计作为系统设计的正式组成部分。
