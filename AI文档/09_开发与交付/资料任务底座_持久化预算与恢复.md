# 资料任务底座：持久化、预算与恢复

本票将既有离线资料核验接入可恢复的单机任务执行，不引入部署、付费调用或自动政策发布。依据SRS OPS-02～05、ACQ-14及数据工具契约§3.1/4/5。

## 成功标准

1. SQLite事务保存run/task/step/attempt/call、输入摘要、处理器版本、步骤输出引用和结构事件；任务状态沿用queued/running/retry_wait/completed/partial/failed/cancelled，终态不覆写，重新运行使用新幂等键并可关联原任务。
2. 任务幂等键关联冻结输入、步骤版本与预算配置；相同键不同输入拒绝。已完成步骤的输出与状态同事务提交；恢复不重复执行这些步骤。
3. 单机租约使用owner与递增epoch；租约失效、取消或超截止后禁止提交结果。进程中断后未发出调用可释放预留，已发出但结果未知记usage_pending，不自动填0。
4. 工具次数、token与整数成本单位先原子预留再执行；结算幂等，实际超估计诚实记账并阻止新调用。调用次数与重试/总时限均有界。
5. 只对已登记为幂等安全的处理器和明确可重试错误重试；退避/Retry-After落盘，不在runner里sleep。403/认证/输入错误不无差别重试，编程错误留失败记录后重抛。
6. 默认真实集成为原资料包校验→既有inspect_applicability；任务输出和所有预算/错误/恢复状态可由CLI查询，未知与partial继续保存。默认不联网、不读取模型配置/密钥。
7. 混合失败、预算不足、取消、崩溃、过期worker、输出/审计事务故障均有反例；全量测试和独立双路复核后再放行。

## 边界

任务产物以SQLite内容寻址记录提交，事务同时写步骤状态和本地事件。它不是正式PublicationRepository。现有文件发布库尚未与任务数据库形成同事务fencing，本票不注册发布处理器，也不声称已完成远端或跨主机exactly-once。后续发布接入须单独兑现该契约，不能把处理器声明为幂等就获得发布权限。

单机CLI协作式取消/超时：调用前后及检查点检查；无法强杀任意同步解析函数。超时后的返回不能提交结果，已发出调用的未知usage保留。退避任务需后续resume/worker调度唤醒，不自主创建系统计划任务。

当前每个run创建一个根任务，步骤共享同一运行预算。parent_task_id仅保存新运行与原任务的关联，不表示已实现层次子任务配额下发。预算tool_calls当前统计已登记的本地操作，内部PDF解析次数仍在业务报告usage中记录；两个默认处理器的token/成本已知为0，并非把未知供应商账单填0。

## 实现、HLD及验证

实现位于`src/yantu/tasks/`：models保存类型与配置不变量，store负责SQLite短事务，runner负责只读版本处理器调度，policy_workflow负责冻结bundle/target与两步实际核验。`scripts/policy_tasks.py`提供submit/resume/show/list/cancel/export；export只导出已提交的applicability报告，不能把manifest检查点冒充最终业务报告。

状态迁移与预算处理：

| 触发 | 状态/行为 |
|---|---|
| 入队/取得租约 | queued→running；校验owner/epoch及截止 |
| 主动步骤检查点 | 完成步骤原子保存后让出为queued，后续不重跑 |
| 明确可重试错误 | running→retry_wait；到next_at后resume，不sleep |
| 全部步骤完成 | completed或partial；源缺损保留partial，业务字段unknown本身不等于执行失败 |
| 预算/截止不足 | 停止新调用；有已完成步骤则partial，否则failed |
| 取消 | 非终态→cancelled，撤销epoch，未发送释放、在途未知保留 |
| 过期worker恢复 | 旧尝试interrupted；未dispatch可释放，已dispatch变usage_pending，次数预算允许才重放 |

### 实现后的HLD分析

先实现并跑通370项全量，再按实际重复改造：

- `_active_task`收拢5处owner/epoch、截止终止及租约有效性检查，状态更新留在调用者事务中；没有抽象成State子类族。
- 独立探针发现写锁等待及事务内部耗时会让初始时间失效。所有变更在BEGIN取得锁后采样；`_assert_commit_window`在事务尾再采样，过期回滚产物、步骤、结算及事件。起始已过截止仍正常提交failed/partial终态，不因抛异常回滚该终止记录。
- `Usage`与`Budget`作为值对象复用计量规则；预算预留/结算仍与状态在同一store，不拆成会丢失事务边界的独立仓储。
- `HandlerRegistry`按实际两种操作及版本分发，属于有真实消费者的Strategy/Registry；只允许明确可重放且effect=read_only的处理器。不给发布/网络调用预建通用插件权限。
- 沿用canonical_json/atomic_write和安全log_failure，后者补充run/task/step/attempt关联字段，不打印任意异常message/cause。

拒绝ORM、多层pass-through仓储、任意工作流DSL、State类族、数据库外的长worker锁以及把工具“只执行一次”作为无法保证的承诺。
